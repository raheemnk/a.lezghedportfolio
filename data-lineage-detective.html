01 — ProblemProblem

Lineage is tribal knowledge, not dataLineage ist stilles Wissen, keine Daten

"Where does this dashboard number actually come from?" is a question data teams usually answer by tracing SQL by hand, across tools, from memory — especially once the logic is split across raw SQL scripts, Python/pandas ETL jobs and dbt models in the same organization, with no single system that understands all three.

"Woher kommt diese Zahl im Dashboard eigentlich?" ist eine Frage, die Datenteams meist von Hand beantworten — SQL-Skripte durchforsten, tool-übergreifend, aus dem Gedächtnis — besonders sobald sich die Logik über rohe SQL-Skripte, Python/pandas-ETL-Jobs und dbt-Modelle in derselben Organisation verteilt, ohne ein einziges System, das alle drei versteht.

Goal: extract lineage automatically from all three source types into one graph, answer "what breaks if I change X" in seconds instead of hours, and trace a specific number back to its exact origin column by column — not just "somewhere in this table".

Ziel: Lineage automatisch aus allen drei Quelltypen in einen einzigen Graphen extrahieren, "was bricht, wenn ich X ändere" in Sekunden statt Stunden beantworten, und eine konkrete Zahl spaltengenau bis zu ihrem Ursprung zurückverfolgen — nicht nur "irgendwo in dieser Tabelle".

02 — TWO GRANULARITIES ON PURPOSE02 — ZWEI GRANULARITÄTEN MIT ABSICHT

Practical propagation + precise tracingPraktische Propagierung + präzise Rückverfolgung

Impact analysis propagates at table level (fast, practical "is X affected — yes/no"), while a separate column-path function answers the actual headline question — sales_kpi_table.revenue traced precisely through monthly_revenue.revenue → orders_clean.amount → orders_raw.amount, never through an unrelated table.

Die Impact-Analyse propagiert auf Tabellenebene (schnell, praktisch "ist X betroffen — ja/nein"), während eine separate Spaltenpfad-Funktion die eigentliche Titelfrage beantwortet — sales_kpi_table.revenue präzise zurückverfolgt über monthly_revenue.revenue → orders_clean.amount → orders_raw.amount, nie über eine unbeteiligte Tabelle.

03 — AST, NOT REGEX03 — AST STATT REGEX

Parsing Python ETL properlyPython-ETL richtig geparst

The Python ETL extractor uses the standard ast module to find pd.read_sql(...) / .to_sql(...) calls — parsing actual syntax rather than pattern-matching on source text, which breaks the moment formatting changes.

Der Python-ETL-Extraktor nutzt das Standardmodul ast, um pd.read_sql(...)/.to_sql(...)-Aufrufe zu finden — echtes Parsen der Syntax statt Mustererkennung im Quelltext, die bei jeder Formatierungsänderung bricht.

04 — A DELIBERATE CONTROL GROUP04 — EINE BEWUSSTE KONTROLLGRUPPE

Proving impact analysis excludes, not just includesBeweis, dass die Impact-Analyse ausschließt, nicht nur einschließt

An intentionally unrelated pipeline (product_catalog) is included in the test graph and explicitly tested to stay out of every impact report it shouldn't appear in — proving the analysis isn't just "return everything".

Eine absichtlich unbeteiligte Pipeline (product_catalog) ist im Testgraphen enthalten und wird explizit darauf getestet, aus jedem Impact-Report herauszubleiben, in dem sie nicht erscheinen sollte — als Beweis, dass die Analyse nicht einfach "alles zurückgibt".

05 — STRICT DECIDE / QUERY SEPARATION05 — STRIKTE TRENNUNG VON ENTSCHEIDEN UND ABFRAGEN

The LLM orchestrates, the graph answersDas LLM orchestriert, der Graph antwortet

Claude only calls real graph-query functions (find_downstream_dependencies, find_upstream_dependencies, get_pipeline_metadata) via tool use and formulates the answer from their results — with a deterministic pattern-matching fallback for offline testing, so the AI layer is never the source of truth.

Claude ruft ausschließlich echte Graph-Abfragefunktionen (find_downstream_dependencies, find_upstream_dependencies, get_pipeline_metadata) per Tool Use auf und formuliert die Antwort aus deren Ergebnissen — mit einem deterministischen Mustererkennungs-Fallback für Offline-Tests, sodass die KI-Schicht nie die Quelle der Wahrheit ist.

04 — What testing surfacedWas das Testen offenlegte

3 real disambiguation bugs, found and fixed3 echte Disambiguierungs-Bugs, gefunden und behoben

Best-effort SQL parsing hits genuine edge cases. All three were found through testing, not assumed away:

Best-Effort-SQL-Parsing stößt auf echte Grenzfälle. Alle drei wurden durch Tests gefunden, nicht einfach angenommen:

  • date_trunc('month', ...) — the quoted literal 'month' was mistaken for a source column name.date_trunc('month', ...) — das Literal 'month' in Anführungszeichen wurde fälschlich als Quellspalte erkannt.
  • SUM(amount) AS revenue — the alias revenue ended up listed among its own sources.SUM(amount) AS revenue — der Alias revenue tauchte in seinen eigenen Quellen auf.
  • JOIN customers_clean c ON ... then c.customer_id — the alias c was dropped, and resolution silently fell back to the first table by appearance order instead of the correct one.JOIN customers_clean c ON ... gefolgt von c.customer_id — der Alias c ging verloren, die Auflösung fiel stillschweigend auf die erste Tabelle in Reihenfolge zurück statt auf die richtige.
  • Vite build-time env vars in Docker — VITE_* variables are frozen at npm run build, not container start. docker-compose.yml passes them as build.args, not runtime environment — a classic trap otherwise.Vite-Build-Time-Umgebungsvariablen in Docker — VITE_*-Variablen werden bei npm run build eingefroren, nicht beim Containerstart. docker-compose.yml übergibt sie als build.args, nicht als Laufzeit-environment — sonst eine klassische Falle.
05 — CodeCode

Resolving which column really is the sourceAuflösen, welche Spalte wirklich die Quelle ist

Excerpt from sql_lineage.py — the function fixing all three disambiguation bugs above: literals stripped before identifier matching, aliases resolved to real table names, and self-referencing aliases excluded.

Ausschnitt aus sql_lineage.py — die Funktion, die alle drei oben genannten Disambiguierungs-Bugs behebt: Literale werden vor dem Identifier-Matching entfernt, Aliase auf echte Tabellennamen aufgelöst, und selbstreferenzierende Aliase ausgeschlossen.

src/extraction/sql_lineage.py
def _colonnes_sources_dun_item(
    item: str, alias_tables: dict[str, str], nom_cible: str | None = None
) -> list[tuple[str | None, str]]:
    # Strip quoted literals first: date_trunc('month', ...) must not
    # treat 'month' as a source column name (bug #1).
    sans_litteraux = re.sub(r"'[^']*'|\"[^\"]*\"", " ", item)

    identifiants = re.findall(r"\b([a-zA-Z_]\w*)(?:\.([a-zA-Z_]\w*))?\b", sans_litteraux)
    sources: list[tuple[str | None, str]] = []
    for premier, second in identifiants:
        if second:  # 'alias.column' form: resolve the alias to its real table
            if premier.lower() not in MOTS_CLES_SQL:
                table_resolue = alias_tables.get(premier)  # bug #3 fix
                sources.append((table_resolue, second))
        elif premier.lower() not in MOTS_CLES_SQL and premier not in alias_tables:
            sources.append((None, premier))  # unqualified: ambiguous if several source tables

    vues, resultat = set(), []
    for table_resolue, colonne in sources:
        cle = (table_resolue, colonne)
        # colonne != nom_cible excludes the target's own alias from its
        # sources: "SUM(amount) AS revenue" must not list revenue itself (bug #2).
        if cle not in vues and colonne != nom_cible:
            vues.add(cle)
            resultat.append((table_resolue, colonne))
    return resultat
06 — Technical Validation & LimitationsTechnische Validierung & Einschränkungen

What has been validatedWas validiert wurde

  • Neo4j integration: Neo4jGraphStore is implemented with real Cypher, ready against the provided docker-compose.yml. Development and testing ran against the equivalent NetworkXGraphStore, as no local Neo4j instance was running; the Cypher path itself was not exercised live.Neo4j-Integration: Neo4jGraphStore ist mit echtem Cypher implementiert, einsatzbereit gegen das mitgelieferte docker-compose.yml. Entwicklung und Tests liefen gegen den äquivalenten NetworkXGraphStore, da keine lokale Neo4j-Instanz lief; der Cypher-Pfad selbst wurde nicht live ausgeführt.
  • SQL parsing: best-effort syntactic extraction, the same category of tool as sqllineage or most market tools, not a full semantic SQL analyzer. A dynamically-built table name in Python, or a deeply nested subquery, may not resolve.SQL-Parsing: Best-Effort-syntaktische Extraktion, dieselbe Werkzeugkategorie wie sqllineage oder die meisten marktüblichen Tools, kein vollständiger semantischer SQL-Analyzer. Ein dynamisch in Python erzeugter Tabellenname oder eine tief verschachtelte Subquery lässt sich unter Umständen nicht auflösen.
  • Impact propagation: table-level by design — once a column changes, the whole table is considered affected downstream. A deliberate trade-off between practicality and precision (justified in the code), with exact column-level tracing available separately.Impact-Propagierung: mit Absicht auf Tabellenebene — sobald sich eine Spalte ändert, gilt die gesamte Tabelle für die weitere Propagierung als betroffen. Ein bewusster Kompromiss zwischen Praktikabilität und Präzision (im Code begründet), mit separat verfügbarer exakter Spaltenrückverfolgung.
  • AI query layer: validated through its deterministic fallback, tested to answer correctly from graph queries alone. No API key was configured for this development pass, so the live Claude tool-use call itself was not validated.KI-Abfrageschicht: über ihren deterministischen Fallback validiert, nachweislich korrekt allein aus Graph-Abfragen beantwortet. Für diesen Entwicklungsdurchlauf war kein API-Schlüssel konfiguriert, daher wurde der eigentliche Live-Tool-Use-Aufruf an Claude nicht validiert.
