A Model Context Protocol server that exposes a PostgreSQL database to an AI agent strictly read-only, protected by three independent security layers and a full audit trail — built to answer a simple question: how do you let an agent explore real data without ever trusting it not to break something?

Ein Model-Context-Protocol-Server, der einer KI eine PostgreSQL-Datenbank strikt schreibgeschützt zur Verfügung stellt, abgesichert durch drei unabhängige Sicherheitsebenen und ein vollständiges Audit-Log — gebaut, um eine einfache Frage zu beantworten: Wie lässt man einen Agenten echte Daten erkunden, ohne ihm je zu vertrauen, nichts kaputtzumachen?

01 — ProblemProblem

Trusting an agent isn't a security modelEinem Agenten zu vertrauen ist kein Sicherheitsmodell

Giving an AI agent direct database access is useful — it can explore schemas, profile tables, answer ad-hoc questions — but "the agent will only run safe queries" is not a security guarantee, whether the risk is a bad instruction, a prompt injection, or the model simply making a mistake. The access layer itself has to make unsafe actions structurally impossible, not just unlikely.

Einem KI-Agenten direkten Datenbankzugriff zu geben ist nützlich — er kann Schemas erkunden, Tabellen profilieren, Ad-hoc-Fragen beantworten — aber "der Agent wird schon nur sichere Abfragen ausführen" ist keine Sicherheitsgarantie, egal ob das Risiko eine schlechte Anweisung, eine Prompt Injection oder ein schlichter Modellfehler ist. Die Zugriffsschicht selbst muss unsichere Aktionen strukturell unmöglich machen, nicht nur unwahrscheinlich.

Goal: an MCP server giving an agent genuinely useful read access — schema exploration, table profiling, ad-hoc SELECT queries — while making every write path fail at more than one independent layer, even if an earlier layer has a bug.

Ziel: ein MCP-Server, der einem Agenten echten, nützlichen Lesezugriff gibt — Schema-Exploration, Tabellenprofilierung, Ad-hoc-SELECT-Abfragen — während jeder Schreibpfad auf mehr als einer unabhängigen Ebene fehlschlägt, selbst wenn eine frühere Ebene einen Fehler hat.

03 — Key decisionsZentrale Entscheidungen

Technical choices, and whyTechnische Entscheidungen — und warum

01 — DEFENSE IN DEPTH01 — DEFENSE IN DEPTH

Three independent layers, each sufficient aloneDrei unabhängige Ebenen, jede für sich ausreichend

An application-level SQL guard, a PostgreSQL role with literal SELECT-only grants, and enforced limits/timeouts. None of the three depends on the others being correct.

Ein SQL Guard auf Anwendungsebene, eine PostgreSQL-Rolle mit ausschließlich SELECT-Rechten und erzwungene Limits/Timeouts. Keine der drei Ebenen hängt davon ab, dass die anderen korrekt sind.

02 — FULL TOKEN SCAN02 — VOLLSTÄNDIGER TOKEN-SCAN

Not just the first keywordNicht nur das erste Schlüsselwort

A query starting with WITH looks like a harmless SELECT if you only check the first word — but PostgreSQL allows data-modifying CTEs, so a DELETE hidden inside one would actually execute. The guard tokenizes the entire query tree with sqlparse and rejects a forbidden keyword anywhere in it.

Eine mit WITH beginnende Abfrage sieht wie ein harmloses SELECT aus, wenn man nur das erste Wort prüft — aber PostgreSQL erlaubt datenverändernde CTEs, sodass ein darin verstecktes DELETE tatsächlich ausgeführt würde. Der Guard tokenisiert den gesamten Abfragebaum mit sqlparse und lehnt ein verbotenes Schlüsselwort an jeder Stelle ab.

03 — DB-LEVEL AS THE REAL GUARANTEE03 — DB-EBENE ALS ECHTE GARANTIE

The guard is a courtesy, the role is the guaranteeDer Guard ist eine Höflichkeit, die Rolle ist die Garantie

mcp_readonly_user holds only SELECT at the database engine level. Even if the SQL guard had a bug, PostgreSQL itself refuses any write with permission denied — verified, not assumed.

mcp_readonly_user besitzt auf Datenbankebene ausschließlich SELECT. Selbst bei einem Fehler im SQL Guard verweigert PostgreSQL selbst jeden Schreibversuch mit permission denied — verifiziert, nicht angenommen.

04 — LIMITS THAT CAN'T BE BYPASSED FROM INSIDE04 — VON INNEN NICHT UMGEHBARE LIMITS

Query wrapping, not query trustAbfrage-Wrapping statt Abfrage-Vertrauen

The user's query is wrapped inside an enclosing SELECT ... LIMIT n, so an internal LIMIT 999999999 is simply ignored. statement_timeout (5s default) is set both at the transaction level and on the role itself — tested with SELECT pg_sleep(10), cut off at 5s as expected.

Die Nutzerabfrage wird in ein umschließendes SELECT ... LIMIT n gepackt, sodass ein internes LIMIT 999999999 schlicht ignoriert wird. statement_timeout (Standard 5s) wird sowohl auf Transaktionsebene als auch auf der Rolle selbst gesetzt — getestet mit SELECT pg_sleep(10), wie erwartet nach 5s abgebrochen.

05 — TAMPER-PROOF AUDIT LOG05 — MANIPULATIONSSICHERES AUDIT-LOG

Local by necessity, not by convenienceLokal aus Notwendigkeit, nicht aus Bequemlichkeit

Every tool call is journaled to an append-only JSONL file. It lives outside the database on purpose: mcp_readonly_user couldn't write to the database even if it wanted to — which means no SQL injection could ever alter the audit trail.

Jeder Tool-Aufruf wird in eine Append-only-JSONL-Datei journalt. Sie liegt absichtlich außerhalb der Datenbank: mcp_readonly_user könnte selbst dann nicht in die Datenbank schreiben, wenn er wollte — sodass keine SQL-Injection je das Audit-Log verändern könnte.

A live security demonstrationEine Live-Sicherheitsdemonstration

Rather than just asserting the guardrails work, the project includes a real transcript — captured through the actual MCP protocol, not a hand-written example — of an agent asked to delete data, and rejected end-to-end.

The 60 demo customers are still there. The project's README also documents three real bugs found and fixed during development — a token-type mismatch in the sensitive-table check, an undocumented PostgreSQL restriction on information_schema for read-only roles, and a FastMCP response-parsing quirk — rather than presenting the build as having gone smoothly.

src/security/sql_guard.py
def valider_lecture_seule(sql: str) -> None:
    """Raises SecurityError if the query isn't a pure, safe SELECT."""
    sql_clean = sql.strip()

    if not sql_clean:
        raise SecurityError("The query is empty.")
    if len(sql_clean) > LONGUEUR_MAX_REQUETE:
        raise SecurityError(f"Query too long (max {LONGUEUR_MAX_REQUETE} chars).")

    # Single statement only: strip at most one trailing ';', then check
    # none remain (blocks stacked queries, e.g. "SELECT 1; DELETE ...").
    without_trailing = re.sub(r";\s*$", "", sql_clean)
    if ";" in without_trailing:
        raise SecurityError("Only one SQL statement per call (no internal ';').")

    statement = sqlparse.parse(without_trailing)[0]
    tokens = _all_tokens(statement)  # recursively flattens CTEs, subqueries

    first_word = next(
        t.value.upper() for t in tokens
        if not t.is_whitespace and t.ttype != sqlparse.tokens.Comment
    )
    if first_word not in ("SELECT", "WITH", "("):
        raise SecurityError(f"Only SELECT (or WITH ... SELECT) is allowed. Found: '{first_word}'.")

    # Scan of ALL tokens, not just the first ones: see the module
    # docstring for the data-modifying-CTE example this guards against.
    for token in tokens:
        if token.ttype in (DML, DDL, Keyword) and token.value.upper() in MOTS_CLES_INTERDITS:
            raise SecurityError(f"Forbidden keyword detected: '{token.value.upper()}'.")
        if token.ttype in (None, sqlparse.tokens.Name) and \
                token.value.lower().strip('"') in TABLES_SENSIBLES_INTERDITES:
            raise SecurityError(f"Access to '{token.value}' is not allowed (sensitive system table).")
06 — Technical Validation & LimitationsTechnische Validierung & Einschränkungen

What has been validatedWas validiert wurde

  • Validated at three levels — unit tests on the SQL guard, integration tests against a real PostgreSQL instance, and a live MCP protocol session (see the transcript above), including the deliberate delete attempt.Auf drei Ebenen validiert — Unit-Tests für den SQL Guard, Integrationstests gegen eine echte PostgreSQL-Instanz und eine Live-MCP-Protokollsitzung (siehe Transkript oben), einschließlich des gezielten Löschversuchs.
  • Single shared read-only role for now — no per-MCP-user granularity yet; the audit log's user field is always mcp_client. Natural extension: OAuth at the MCP transport level.Aktuell eine gemeinsame Read-Only-Rolle — noch keine Granularität pro MCP-Nutzer; das user-Feld im Audit-Log ist immer mcp_client. Naheliegende Erweiterung: OAuth auf MCP-Transportebene.
  • find_anomalies out of scope for this phase — mentioned in the original design, deliberately left for a later iteration: statistical outliers (z-score) on profile_table's numeric columns, duplicate detection, data-freshness gaps.find_anomalies außerhalb des Umfangs dieser Phase — im ursprünglichen Design erwähnt, bewusst für eine spätere Iteration zurückgestellt: statistische Ausreißer (Z-Score) in den numerischen Spalten von profile_table, Duplikaterkennung, Frische-Lücken der Daten.
  • Deny-list rather than a full grammar allow-list — simpler to maintain; the PostgreSQL role permissions are the actual backstop by design, independent of this layer.Deny-List statt vollständiger Grammatik-Allow-List — einfacher zu pflegen; die PostgreSQL-Rollenrechte sind bewusst die eigentliche Absicherung, unabhängig von dieser Ebene.
