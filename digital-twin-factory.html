01 — ProblemProblem

Predictive maintenance fails on the boring partsPredictive Maintenance scheitert an den unspektakulären Details

A flashy ML model is the easy part. The parts that actually decide whether a predictive-maintenance system is trustworthy are less glamorous: does an anomaly detector's own adaptive baseline eventually swallow a real, sustained failure? Does the alert status flicker every time a reading sits near the edge? And when an LLM is added to explain a diagnosis, does it stay honest about the numbers, or start inventing plausible-sounding ones?

Ein beeindruckendes ML-Modell ist der leichte Teil. Was wirklich darüber entscheidet, ob ein Predictive-Maintenance-System vertrauenswürdig ist, ist weniger glanzvoll: Schluckt die eigene adaptive Baseline eines Anomalie-Detektors irgendwann einen echten, anhaltenden Fehler? Flackert der Alarmstatus bei jeder grenzwertigen Messung? Und bleibt ein LLM, das eine Diagnose erklären soll, bei den echten Zahlen, oder erfindet es plausibel klingende?

Goal: simulate a realistic industrial pipeline end to end and deliberately stress-test these failure modes — then document what actually broke and how it was fixed, rather than only showing the version that works.

Ziel: eine realistische industrielle Pipeline durchgängig simulieren und diese Fehlermodi gezielt auf die Probe stellen — und dokumentieren, was dabei tatsächlich kaputtging und wie es behoben wurde, statt nur die funktionierende Version zu zeigen.

02 — ArchitectureArchitektur

7 phases, sensors to explanation7 Phasen, von Sensoren zur Erklärung

Each machine streams 5 correlated sensors (temperature, pressure, vibration, rpm, energy) through Kafka into a stream processor that runs detection and prediction together, backed by a time-series store, surfaced on a live dashboard, with an AI layer added last — strictly for explanation.

Jede Maschine streamt 5 korrelierte Sensorwerte (Temperatur, Druck, Vibration, Drehzahl, Energie) über Kafka in einen Stream-Prozessor, der Erkennung und Vorhersage gemeinsam ausführt, gestützt auf einen Zeitreihenspeicher, sichtbar auf einem Live-Dashboard, mit einer zuletzt hinzugefügten KI-Schicht — ausschließlich zur Erklärung.

03 — Key decisionsZentrale Entscheidungen

Technical choices, and whyTechnische Entscheidungen — und warum

01 — DUAL MESSAGE BUS01 — DUALER MESSAGE BUS

Same interface, real and in-memoryGleiches Interface, real und im Speicher

A single MessageBus interface has two implementations: a real KafkaBus (kafka-python, native protocol) ready against the provided docker-compose.yml, and an InMemoryBus with no broker dependency, used to validate every business rule end-to-end without a running Kafka broker.

Ein einziges MessageBus-Interface hat zwei Implementierungen: ein echter KafkaBus (kafka-python, natives Protokoll), einsatzbereit gegen das mitgelieferte docker-compose.yml, und ein InMemoryBus ohne Broker-Abhängigkeit, mit dem jede Geschäftsregel durchgängig validiert wurde, ohne dass ein Kafka-Broker lief.

02 — THREE-TIER DETECTION02 — DREISTUFIGE ERKENNUNG

Each tier catches what the others missJede Stufe erkennt, was die anderen übersehen

A hard threshold that never adapts (a real safety net), a statistical z-score with a per-machine rolling baseline, and a multivariate isolation forest that catches combinations of individually-plausible values that no single z-score can see.

Ein harter threshold, der sich nie anpasst (ein echtes Sicherheitsnetz), ein statistical Z-Score mit gleitender Baseline pro Maschine, und ein multivariater isolation forest, der Kombinationen einzeln plausibler Werte erkennt, die kein einzelner Z-Score sehen kann.

03 — HYSTERESIS ON STATUS03 — HYSTERESE BEIM STATUS

No alert flappingKein Alert-Flapping

An anomaly raises the displayed status immediately, but it only drops back down after several consecutive clean readings — otherwise a borderline sensor value would flip the status back and forth on every single reading.

Eine Anomalie hebt den angezeigten Status sofort an, senkt ihn aber erst nach mehreren aufeinanderfolgenden sauberen Messungen wieder — sonst würde ein grenzwertiger Sensorwert den Status bei jeder einzelnen Messung hin und her kippen lassen.

04 — LOCAL DEVIATION, NOT GLOBAL IMPORTANCE04 — LOKALE ABWEICHUNG, NICHT GLOBALE WICHTIGKEIT

Actionable per-case indicatorsHandlungsrelevante fallbezogene Indikatoren

The "main indicators" shown for a prediction (e.g. "vibration +132%") are each sensor's %-deviation from THAT specific machine's own baseline — not the Random Forest's overall feature importance, which says nothing about the case at hand.

Die für eine Vorhersage angezeigten "Hauptindikatoren" (z. B. "Vibration +132 %") sind die %-Abweichung jedes Sensors von der eigenen Baseline DIESER spezifischen Maschine — nicht die globale Feature-Wichtigkeit des Random Forest, die über den konkreten Fall nichts aussagt.

05 — STRICT DECIDE / EXPLAIN SEPARATION05 — STRIKTE TRENNUNG VON ENTSCHEIDEN UND ERKLÄREN

The LLM never sees raw sensorsDas LLM sieht nie Rohsensordaten

Claude receives only already-structured context (status, Random Forest prediction, recent anomalies, maintenance history) with an explicit instruction not to invent numbers — with a deterministic fallback template used whenever no API key is configured, so the system never fails on missing credentials.

Claude erhält ausschließlich bereits strukturierten Kontext (Status, Random-Forest-Vorhersage, jüngste Anomalien, Wartungshistorie) mit der expliziten Anweisung, keine Zahlen zu erfinden — mit einer deterministischen Fallback-Vorlage, wenn kein API-Schlüssel konfiguriert ist, sodass das System bei fehlenden Zugangsdaten nie fehlschlägt.

04 — What testing surfacedWas das Testen offenlegte

A real detector blind spot, found and fixedEine echte Erkennungslücke, gefunden und behoben

Testing with repeated realistic data over long periods surfaced a classic trap: a rolling z-score adapts to a sustained drift and eventually stops flagging it once the degraded state becomes "the new normal" of its own window. Two concrete fixes followed: the simulator's degradation profile was calibrated so a stable CRITICAL state also reliably crosses the hard threshold detector (which never adapts), and the stream processor combines reactive detection with the Random Forest prediction — with hysteresis — to decide the displayed status, rather than trusting the adaptive detector alone.

Tests mit wiederholten realistischen Daten über lange Zeiträume deckten eine klassische Falle auf: Ein gleitender Z-Score passt sich an eine anhaltende Drift an und hört irgendwann auf, sie zu melden, sobald der degradierte Zustand zur "neuen Normalität" seines eigenen Fensters wird. Zwei konkrete Korrekturen folgten: Das Degradationsprofil des Simulators wurde so kalibriert, dass ein stabiler CRITICAL-Zustand auch zuverlässig den harten Schwellenwert-Detektor überschreitet (der sich nie anpasst), und der Stream-Prozessor kombiniert reaktive Erkennung mit der Random-Forest-Vorhersage — inklusive Hysterese —, um den angezeigten Status zu bestimmen, statt sich allein auf den adaptiven Detektor zu verlassen.

  • Race condition in InMemoryBus.drain() — it checked queue.empty(), not whether processing had actually finished; a message can be "gotten" while its handler is still running. Fixed with task_done()/unfinished_tasks, the mechanism queue.Queue provides for exactly this.Race Condition in InMemoryBus.drain() — geprüft wurde queue.empty(), nicht ob die Verarbeitung tatsächlich abgeschlossen war; eine Nachricht kann "geholt" werden, während ihr Handler noch läuft. Behoben mit task_done()/unfinished_tasks, dem dafür vorgesehenen Mechanismus von queue.Queue.
  • New PostgreSQL connection on every call in FactoryRepository — a real bottleneck for a high-frequency streaming pipeline. Replaced with a psycopg2.pool.ThreadedConnectionPool.Neue PostgreSQL-Verbindung bei jedem Aufruf in FactoryRepository — ein echter Engpass für eine hochfrequente Streaming-Pipeline. Ersetzt durch einen psycopg2.pool.ThreadedConnectionPool.

def predire(self, lectures_recentes: list[dict], baseline: dict) -> Prediction:
    if not self._entraine:
        raise RuntimeError("Model must be trained (entrainer()) before predicting.")
    if len(lectures_recentes) < TAILLE_FENETRE:
        raise ValueError(f"Need at least {TAILLE_FENETRE} recent readings to predict.")

    fenetre = lectures_recentes[-TAILLE_FENETRE:]
    features = _features_fenetre(fenetre, baseline)
    proba = self._predire_proba(features)

    # "Main indicators" = each sensor's LOCAL %-deviation from THIS
    # machine's own baseline — not the forest's global feature
    # importance, which says nothing about this specific case.
    deviations = sorted(
        ((c, features[f"{c}_deviation_pct"]) for c in CAPTEURS),
        key=lambda t: abs(t[1]), reverse=True,
    )
    top_features = [
        {"feature": capteur, "contribution_pct": round(dev, 1)}
        for capteur, dev in deviations[:3]
    ]

    return Prediction(
        failure_probability=round(proba, 4),
        risk_level=self._niveau_risque(proba),
        top_features=top_features,
    )
06 — Technical Validation & LimitationsTechnische Validierung & Einschränkungen

What has been validatedWas validiert wurde

  • Kafka integration: KafkaBus is implemented and configured for the provided Docker environment. End-to-end validation during development ran against the equivalent InMemoryBus, as no local Kafka broker was running; the Kafka implementation itself was not exercised live.Kafka-Integration: KafkaBus ist implementiert und für die mitgelieferte Docker-Umgebung konfiguriert. Die Ende-zu-Ende-Validierung während der Entwicklung lief gegen den äquivalenten InMemoryBus, da kein lokaler Kafka-Broker lief; die Kafka-Implementierung selbst wurde nicht live ausgeführt.
  • LLM diagnosis: the AI layer includes a deterministic fallback mode, tested to never invent a numerical value. No API key was configured for this development pass, so the live Claude call itself was not validated.LLM-Diagnose: Die KI-Schicht enthält einen deterministischen Fallback-Modus, der nachweislich nie einen Zahlenwert erfindet. Für diesen Entwicklungsdurchlauf war kein API-Schlüssel konfiguriert, daher wurde der eigentliche Live-Aufruf an Claude nicht validiert.
  • Anomaly detection: with a z-score threshold of 2.5 and no multi-test correction, a small number of false-positive WARNING results appeared on healthy machines across 6 machines × 5 sensors × 150 readings. These results were kept and reported rather than tuned away. A production deployment would apply a stricter threshold or a correction (Bonferroni or similar) as the number of monitored sensors grows.Anomalieerkennung: Bei einem Z-Score-Schwellenwert von 2,5 ohne Mehrfachtest-Korrektur traten über 6 Maschinen × 5 Sensoren × 150 Messungen vereinzelt WARNING-Falschmeldungen bei gesunden Maschinen auf. Diese Ergebnisse wurden beibehalten und berichtet statt wegkalibriert. Ein Produktiveinsatz würde einen strengeren Schwellenwert oder eine Korrektur (Bonferroni o. ä.) anwenden, sobald die Zahl überwachter Sensoren wächst.
