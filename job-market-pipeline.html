01 — ProblemProblem

Job boards duplicate silentlyJobbörsen duplizieren still und leise

Job aggregators routinely list the same posting more than once — the same role, reworded slightly, published on several platforms — with no cross-source deduplication and no visibility into how long a posting actually stays open. Anyone trying to measure real hiring activity (which roles are actually growing, how long they take to fill) has to do that reconciliation themselves.

Job-Aggregatoren listen dieselbe Stelle regelmäßig mehrfach auf — dieselbe Rolle, leicht anders formuliert, auf mehreren Plattformen veröffentlicht — ohne quellenübergreifende Deduplizierung und ohne Einblick, wie lange eine Stelle tatsächlich offen bleibt. Wer die reale Einstellungsaktivität messen will (welche Rollen wirklich wachsen, wie lange die Besetzung dauert), muss diesen Abgleich selbst vornehmen.

Goal: a pipeline that ingests raw postings without judgment, then deliberately and traceably reconciles duplicates, tracks each posting's lifecycle over time, and surfaces the resulting KPIs — rather than presenting a single daily snapshot as if it were the whole picture.

Ziel: eine Pipeline, die Rohdaten ohne Vorabbewertung aufnimmt, Duplikate anschließend gezielt und nachvollziehbar zusammenführt, den Lebenszyklus jeder Stelle über die Zeit verfolgt und die daraus resultierenden KPIs sichtbar macht — statt eine einzelne Tagesmomentaufnahme als Gesamtbild auszugeben.

A classic data-engineering separation: raw data lands untouched, gets loaded into a staging table where duplicates are expected, then a dedicated step reconciles and historizes it into a clean core schema that analytics and the dashboard both read from.

Eine klassische Data-Engineering-Trennung: Rohdaten landen unverändert, werden in eine Staging-Tabelle geladen, in der Duplikate erwartet werden, und ein eigener Schritt führt sie anschließend zusammen und historisiert sie in ein sauberes Core-Schema, aus dem sowohl Analytics als auch das Dashboard lesen.

03 — Key decisionsZentrale Entscheidungen

Technical choices, and whyTechnische Entscheidungen — und warum

01 — LANDING ZONE01 — LANDING ZONE

Raw ingestion, no upfront cleaningRohe Ingestion, keine Bereinigung im Voraus

Data lands in staging.offres_brutes exactly as the APIs returned it, duplicates included on purpose ("Data Engineer H/F" from Remotive and "Data Engineer (M/F)" from Arbeitnow both land as-is). Reconciliation happens later, deliberately, as its own auditable step — not silently during ingestion.

Daten landen in staging.offres_brutes genau so, wie die APIs sie geliefert haben, Duplikate absichtlich inklusive ("Data Engineer H/F" von Remotive und "Data Engineer (M/F)" von Arbeitnow landen unverändert). Der Abgleich erfolgt später, bewusst, als eigener nachvollziehbarer Schritt — nicht stillschweigend während der Ingestion.

02 — DEDUPLICATION KEY02 — DEDUPLIZIERUNGSSCHLÜSSEL

Normalized slug, exact matchNormalisierter Slug, exakter Abgleich

A unique key slug(title) | slug(company) | slug(city), with gender markers (H/F, M/F...) and legal-form suffixes stripped. Deliberate limitation, stated in the README rather than hidden: this is exact-key matching, not fuzzy matching (Levenshtein, embeddings) — "Data Engineer" and "Ingénieur Data" would still be counted as two postings.

Ein eindeutiger Schlüssel slug(titel) | slug(firma) | slug(stadt), wobei Geschlechtsmarker (H/F, M/F...) und Rechtsformzusätze entfernt werden. Bewusste, im README genannte statt versteckte Einschränkung: Es handelt sich um exakten Schlüsselabgleich, nicht um Fuzzy-Matching (Levenshtein, Embeddings) — "Data Engineer" und "Ingénieur Data" würden weiterhin als zwei Stellen gezählt.

03 — COMPANY RECONCILIATION03 — FIRMEN-ABGLEICH

City-suffix heuristicStadt-Suffix-Heuristik

Some aggregators suffix the company name with the city ("TechCorp Paris"). When that suffix exactly matches the posting's city field, it's stripped — reconciling "TechCorp" (source A) with "TechCorp Paris" (source B) as one company.

Manche Aggregatoren hängen die Stadt an den Firmennamen an ("TechCorp Paris"). Stimmt dieser Zusatz exakt mit dem Stadtfeld der Stelle überein, wird er entfernt — so werden "TechCorp" (Quelle A) und "TechCorp Paris" (Quelle B) als eine Firma zusammengeführt.

04 — HISTORIZATION VIA TRIGGERS04 — HISTORISIERUNG PER TRIGGER

PL/pgSQL, not application logicPL/pgSQL statt Anwendungslogik

Status transitions are logged automatically by two PostgreSQL triggers — never a DELETE. A posting not seen in the last 3 collection runs flips from Active to Expirée, and the transition is journaled by the database itself, so the Python layer can't forget to log it.

Statusübergänge werden automatisch von zwei PostgreSQL-Triggern protokolliert — nie ein DELETE. Eine Stelle, die in den letzten 3 Collection-Läufen nicht gesehen wurde, wechselt von Active zu Expirée, und der Übergang wird von der Datenbank selbst journaled — die Python-Schicht kann es nicht vergessen.

05 — TESTING05 — TESTING

Unit + replayed-integration + CIUnit + nachgespielte Integration + CI

Pure unit tests need no database. An integration test replays 5 simulated collection days and verifies: two sources merge into one posting, "Société Générale" and "SOCIETE GENERALE SA" merge into one company, and expiration triggers automatically after 3 missed collections. GitHub Actions runs the full suite against a real Postgres container on every push.

Reine Unit-Tests benötigen keine Datenbank. Ein Integrationstest spielt 5 simulierte Collection-Tage nach und prüft: zwei Quellen führen zu einer Stelle zusammen, "Société Générale" und "SOCIETE GENERALE SA" führen zu einer Firma zusammen, und der Status wechselt automatisch nach 3 verpassten Collections. GitHub Actions führt die komplette Suite bei jedem Push gegen einen echten Postgres-Container aus.

04 — CodeCode

Historization, at the database levelHistorisierung auf Datenbankebene

Excerpt from the trigger that journals every status change into core.offres_historique — AFTER INSERT OR UPDATE because the history table has a foreign key back to core.offres, so the parent row must exist first.

Ausschnitt aus dem Trigger, der jede Statusänderung in core.offres_historique journalt — AFTER INSERT OR UPDATE, weil die History-Tabelle einen Fremdschlüssel auf core.offres hat und die übergeordnete Zeile daher zuerst existieren muss.

db/init/003_triggers_historisation.sql
CREATE OR REPLACE FUNCTION core.fn_historiser_changement_statut()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO core.offres_historique (id_offre, ancien_statut, nouveau_statut, commentaire)
        VALUES (NEW.id_offre, NULL, NEW.statut, 'Création de l''offre');
        RETURN NEW;
    END IF;

    IF TG_OP = 'UPDATE' AND NEW.statut IS DISTINCT FROM OLD.statut THEN
        INSERT INTO core.offres_historique (id_offre, ancien_statut, nouveau_statut, commentaire)
        VALUES (
            NEW.id_offre,
            OLD.statut,
            NEW.statut,
            CASE
                WHEN NEW.statut = 'Expirée' THEN 'Offre non revue lors des 3 dernières collectes'
                WHEN NEW.statut = 'Active' THEN 'Offre republiée / revue à nouveau'
                ELSE NULL
            END
        );
    END IF;

    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_historiser_statut
    AFTER INSERT OR UPDATE ON core.offres
    FOR EACH ROW
    EXECUTE FUNCTION core.fn_historiser_changement_statut();

06 — Technical Validation & LimitationsTechnische Validierung & Einschränkungen

What has been validatedWas validiert wurde

  • Validated end-to-end: unit tests, an integration test replaying 5 simulated collection days against a real PostgreSQL container, and GitHub Actions running the full suite on every push.Durchgängig validiert: Unit-Tests, ein Integrationstest mit 5 nachgespielten Collection-Tagen gegen einen echten PostgreSQL-Container, und GitHub Actions führt die komplette Suite bei jedem Push aus.
  • Deduplication: exact-key matching only — genuinely differently-worded postings for the same role aren't merged. Fuzzy matching (Levenshtein, embeddings) is a planned next step.Deduplizierung: nur exakter Schlüsselabgleich — tatsächlich unterschiedlich formulierte Stellen für dieselbe Rolle werden nicht zusammengeführt. Fuzzy-Matching (Levenshtein, Embeddings) ist als nächster Schritt geplant.
  • Historization: a single run is only a snapshot — the expiration logic only becomes meaningful after several days of repeated collection.Historisierung: ein einzelner Lauf ist nur eine Momentaufnahme — die Ablauflogik entfaltet ihren Sinn erst nach mehreren Tagen wiederholter Collection.
  • Deployment: local Docker Compose only, not yet deployed to a cloud environment or scheduled automatically outside CI.Deployment: bislang nur lokales Docker Compose, noch nicht in einer Cloud-Umgebung bereitgestellt oder außerhalb der CI automatisch geplant.
